## Impact Taxonomy

Every finding must map to ONE category:

- **REVENUE_LEAK** — N/A for a free, self-hosted product
- **SUPPORT_BURDEN** — stuck UI, wrong data shown, lost work, broken flows
- **DATA_LOSS** — user upload destroyed, reading progress wiped, annotations corrupted, library wrongly delisted
- **SECURITY_BREACH** — cross-user data leak, unauth access to admin endpoints, RCE, privilege escalation, SSRF to internal network
- **COMPLIANCE** — N/A (no regulatory exposure)
- **PROD_INCIDENT** — server crash loop, OOM, deadlock, single-handler unresponsiveness
- **BRAND_DAMAGE** — public-facing failure on a self-hosted server (e.g., open-redirect, leak of one user's email)

## Severity Calibration

### The CRITICAL test
Label CRITICAL when a real user on a real configuration would lose money, lose data, lose access, or hit a full outage as a consequence. The bug must fire **in practice** under defaults or a realistic attacker path.

For Biblioteka specifically:
- **Default config = SQLite, single-instance, exposed via reverse proxy with auth**. This is the most-likely real deployment.
- "Multi-user instance" = family/household (2–10 users). A bug that lets user A read user B's reading progress, annotations, credentials, or uploaded books is CRITICAL even at that scale because it's a complete trust violation and there's no realistic mitigation the user can deploy.
- "Unauth access" or "admin bypass" is always CRITICAL — anyone running this on a public IP is exposed.
- "Books shared across users" is **NOT** a finding (it's the documented design).

### Severity bands
- **CRITICAL** — unauth access to authenticated endpoints; cross-user data leak; cross-tenant write; auth bypass; unrecoverable data destruction; RCE; SSRF to internal infra; full process crash on a primary flow.
- **HIGH** — visible bug on a primary flow affecting all users in a recurring way; reflected/stored XSS in core UI; persistent denial of metadata extraction; auth weakening (e.g., MD5 not constant-time); broken audit logging on a sensitive action; lost-work on a frequent flow.
- **MEDIUM** — real bug, user-visible consequence, workaround exists; auth boundary degradations that require a specific niche misconfiguration; rare data loss; broken edge cases on rare flows.
- **LOW** — defense-in-depth; lint-level; insufficient documentation.

## Critical Workflow Ledger

### Workflow 1: First-user auto-promote
- Invariant: First successful signup → `is_admin=true`. Subsequent signups → not admin.
- Entry points: `POST /api/auth/signup`
- Writers: `users` table insert; potential admin flag set.
- Transaction boundary: depends on goauth implementation; needs verification.
- Retry / replay: client retries (e.g., 504 from upstream proxy) could fire two signups for the same email — second should fail on unique constraint, but the **race between two concurrent signups for the FIRST account** is the deep risk: both could insert with `is_admin=true` if `COUNT(*)` check is non-transactional.
- Why fails only in prod: requires near-simultaneous signups at instance-init time.

### Workflow 2: KOSync progress put
- Invariant: progress for `(user_id, document)` is the latest write that arrives.
- Entry points: `PUT /api/syncs/progress`
- Writers: `reading_progress` table.
- Retry / replay: KOReader retries aggressively when offline; many devices for the same user can collide on the same document; a stale write arriving after a fresh one would lose data.
- Why fails only in prod: requires multi-device or flaky network.

### Workflow 3: Watch-folder scan + file process
- Invariant: a file appearing in the watch folder is processed exactly once.
- Entry points: cron `scan:watch-folder` (every 1m); manual library scan.
- Writers: `books`, `book_files`, sidecar files on disk.
- Retry: asynq up to 5 retries with backoff.
- Dedup: `WithUnique(24*time.Hour)` on file path.
- Race: a file moved within the watch folder mid-scan; concurrent scans by overlapping cron firings; a file processed by `process:file` while `scan:watch-folder` enqueues it again.
- Why fails only in prod: large libraries + frequent file system changes + 24h dedup window mismatches.

### Workflow 4: Book upload → metadata extract → cover decode → sidecar write
- Invariant: an uploaded file appears as a usable book with correct metadata, or the upload is fully rejected (no orphan files).
- Entry points: `POST /api/books/upload`, `POST /api/books/{id}/files`.
- Writers: filesystem (staged path), `books` table, `book_files` table, cover image files, sidecar OPF.
- Transaction boundary: `CreateBookWithFile` is wrapped in a tx for DB rows, but staged file and sidecar writes are not in the same atomic unit.
- Retry: asynq retries `process:file` up to 5 times. Each retry could write another sidecar/cover.
- Cleanup: on upload error, staged file is removed; on `process:file` failure, the staged file may be left behind.
- Why fails only in prod: large files, slow disks, retry storms, server restart mid-process.

### Workflow 5: OIDC callback → user creation → JWT issuance
- Invariant: a user authenticated via OIDC gets a session bound to their oidc_subject. New users only get accounts if registration is enabled.
- Entry points: `GET /api/auth/oidc/callback`
- Writers: `users` insert (on first OIDC login).
- Race: the registration gate check (`registration_disabled` setting) is read NON-transactionally before goauth issues the JWT — admin toggling the setting between check and write could leak signups.
- Why fails only in prod: misconfigured registration gate + concurrent admin/user actions.

### Workflow 6: Library delete cascading
- Invariant: deleting a library removes its books or detaches them safely. No orphaned `library_books`, no half-deleted state.
- Entry points: `DELETE /api/libraries/{id}`
- Writers: `libraries`, `library_books`, possibly `books`, possibly `book_files`, filesystem.
- Risk: shared across users; one user's delete affects another user's bookshelf.

### Workflow 7: Group annotation visibility
- Invariant: an annotation marked group-visible is only visible to (a) the author and (b) members of the group; private annotations only to the author.
- Entry points: `GET /api/books/{id}/annotations`, `GET /api/annotations/{id}`.
- Recent fix: `9f9a153f` — `GetAnnotation` now includes group-visible annotations for members. The reverse risk (returning private annotations to non-author group members) is the deep bug.
- Why fails only in prod: requires multiple users in the same group simultaneously.

### Workflow 8: Send-to-device email
- Invariant: book file is emailed to the recipient address the user configured for themselves; recipient address is validated before SMTP RCPT TO.
- Entry points: `POST /api/book-files/{id}/email`.
- Risk: the SMTP package does NOT validate recipients; if the handler also doesn't, a user could trigger arbitrary outbound mail through the server.

### Workflow 9: Goodreads/Open Library lookup with user-controlled query
- Invariant: user-controlled query text is sent to Goodreads safely; SSRF is impossible (endpoint is hardcoded).
- Risk: Goodreads client uses `http.DefaultTransport` (no SSRF wrapper). If the endpoint is ever made user-configurable, this is a one-line bypass.

## Integration Map

### Integration: Frontend → Backend
- Contract: REST `/api/*` returning JSON; SSE for metadata events.
- Source files: `frontend/src/lib/api.ts`, components/stores.
- Target files: `internal/handlers/`.
- Auth coupling: JWT cookie shared across both halves (`biblioteka_token`).
- Version coupling: embedded build — frontend ships with backend; mismatch impossible on a clean deploy.
- Highest-risk failure: SSE handler (`GET /api/books/{id}/metadata/events`) — long-lived connection, must enforce per-user scoping.

### Integration: KOReader → KOSync endpoints
- Contract: KOReader spec for `/api/user/auth`, `/api/syncs/progress`.
- Source: external (KOReader app).
- Target: `internal/handlers/kosync.go`.
- Auth coupling: `x-auth-user`/`x-auth-key` headers; key is hex-MD5 of password, server compares bcrypt(received_hex).
- Highest-risk failure: progress overwrite race when multiple devices sync the same document; weak MD5 hashing surface if client trusted store leaks.

### Integration: Kobo device → /kobo/{token} routes
- Contract: Kobo proprietary API (init, auth, library/sync, library/{uuid}/state, library/{uuid}/metadata, download, covers).
- Source: external (Kobo firmware).
- Target: `internal/handlers/kobo_*.go`.
- Auth coupling: token in URL path; SHA-256 hashed in DB. Path is rewritten after middleware extracts token.
- Highest-risk failure: token leakage via reverse proxy logs; uuid-keyed state endpoints that don't verify book belongs to user.

### Integration: OPDS clients → /opds
- Contract: OPDS 1.x XML feeds, Basic Auth.
- Source: external (Tolino, Aldiko, KyBook, etc.).
- Target: `internal/handlers/opds*.go`, `internal/opds/`.
- Highest-risk failure: download endpoint serving any user's book file (auth check must scope by user); cover URL XML encoding; pagination cursor smuggling.
